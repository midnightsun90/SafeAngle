# SafeAngle 데이터 저장 구조

## 데이터는 이렇게 연결된다

**관리자 1명 → 평가 대상자 여러 명 → 대상자별 평가 여러 건 → 평가마다 영상 최대 3개**

관리자와 평가 대상자는 서로 다른 사람이다. 같은 대상자를 다시 평가하면 이전 기록을 덮어쓰지 않고 새 평가를 추가한다.

| 저장 항목 | 내용 |
| --- | --- |
| 관리자 | 이름, 관리자 구별 번호 |
| 평가 대상자 | 이름, 담당 관리자 |
| 평가 | 대상자, 진행 상태. 분석 이후 값과 결과를 위한 기존 칸은 유지 |
| 자세별 평가 입력 | 촬영 여부, 선택 장면 시각, 작업 조건 답변 |
| 영상 기록 | 촬영 자세 종류, 비공개 영상 파일의 위치 |

## v6 평가 입력: 분석 시작 전까지

기존 [v6 화면 시안](../design/frontend-flow-v6.excalidraw)에서 회사·작업 입력 단계를 제거한 흐름이다. 번호는 현재 화면과 DB 항목을 연결하기 위한 번호다. 질문이 바뀌어도 답변은 `answers` JSON 안에서 질문 번호로 구분하고 `question_schema_version`을 함께 기록한다.

| 번호 | 화면에서 입력하는 값 | DB 위치 |
| --- | --- | --- |
| 1-1 | 물체를 들어 옮기는 작업 영상 또는 건너뛰기 | `assessment_videos` 파일 기록 + `assessment_posture_inputs.is_skipped` (`lift_transfer`) |
| 1-2 | 앉아서 손으로 하는 작업 영상 또는 건너뛰기 | 위와 같음 (`seated_handwork`) |
| 1-3 | 물체를 밀거나 당기는 작업 영상 또는 건너뛰기 | 위와 같음 (`push_pull`) |
| 2-1~2-3 | 각 영상에서 선택한 평가 장면의 시각(초) | 자세별 `assessment_posture_inputs.selected_time_seconds` |
| Q2-1 | 물체 무게 또는 실제 사용한 힘: 5 kg 미만 / 5~10 kg / 10 kg 초과 / 확인 불가 | 자세별 `answers.q2_1` |
| Q2-2 | 충격·갑작스러운 힘 사용: 있음 / 없음 / 확인 불가 | 자세별 `answers.q2_2` |
| Q3 | 물체를 잡거나 지지하는 상태: 좋음 / 보통 / 나쁨 / 부적절 / 해당 없음 / 확인 불가 | 자세별 `answers.q3` |
| Q4-1 | 한 부위를 같은 자세로 1분 이상 유지: 예 / 아니요 / 확인 불가 | 자세별 `answers.q4_1` |
| Q4-2 | 좁은 범위에서 분당 4회 이상 반복(걷기 제외): 예 / 아니요 / 확인 불가 | 자세별 `answers.q4_2` |

영상 파일명과 읽을 수 있는 길이는 `assessment_videos.original_filename`, `duration_seconds`에 기록한다. 브라우저가 길이를 읽지 못하면 null로 남긴다. 파일이 없는 자세도 건너뛰기 여부와 답변을 구분할 수 있도록 자세별 입력 표는 평가당 최대 3행을 쓴다. 건너뛴 자세에는 장면 시각과 질문 답변을 넣지 않는다. 세 자세를 모두 건너뛰면 분석을 시작할 수 없다.

회사명·사업장·공정·작업명 입력 단계는 제거했다. `assessments.company_name`, `workplace`, `work_process`, `work_name` 열도 삭제했다. 기존 `assessments.answers`는 구 구조와의 호환을 위해 남겨 두고, 자세별 질문은 새 표의 `answers`에 저장한다.

v6의 **Q4-3은 분석 후 필요할 때 장면을 보며 확인**한다고 적혀 있으므로 이 단계의 필수 답변에서 제외한다. 분석 이후의 측정·점수·결과 표는 이번 변경 범위에 넣지 않았다.

영상 파일은 `assessment-videos`라는 비공개 저장소에 둔다. 평가 기록에는 영상 파일의 **위치만** 적는다. 영상 위치는 공개 주소가 아니다. 영상 하나의 현재 업로드 한도는 50 MB다.

질문에 답하지 못했거나 영상에서 측정할 수 없는 값은 **미확인**으로 남기고 0점으로 바꾸지 않는다. 평가를 `완료` 상태로 저장하려면 결과와 REBA 점수가 둘 다 있어야 한다. 점수 기준은 [평가표](evaluation-axes.md)에 있다.

## 누가 볼 수 있나

- 관리자는 자신이 등록한 평가 대상자와 평가, 영상만 볼 수 있다.
- 다른 관리자의 기록은 볼 수 없다.
- 관리자 이름은 화면에 보여 주는 값이다. **이름이 같다는 이유로 다른 사람의 기록에 들어갈 수 없다.**
- 심사위원용 공개 시연 페이지에는 예시 데이터만 보여 준다.

## 지금까지 만든 것

- [Supabase SafeAngle 프로젝트](https://supabase.com/dashboard/project/ixocecrvriaprwynhnst)에 관리자·평가 대상자·평가·자세별 평가 입력·영상 기록 표 5개를 만들었다.
- 비공개 영상 저장소와 관리자별 접근 제한을 설정했다. 보안 점검 결과 오류 0건이다. 익명 로그인 허용 등에 관한 경고 7건은 남아 있다.
- DB를 처음 구성할 때는 저장된 평가와 영상이 없었다. 이 문서의 현재 작업에서 원격 데이터 개수는 재확인하지 않았다.
- 웹 화면의 관리자 이름과 평가 대상자 이름은 DB에 저장된다. 같은 브라우저에서는 새로고침 후 다시 불러온다.
- 이름 입력 시 익명 로그인으로 관리자 구별 번호를 만든다. 브라우저 데이터를 지우거나 다른 기기를 사용하면 이전 기록에 다시 접근할 수 없다.

## 아직 연결하지 않은 것

- 원 세션의 실제 VLM 결과 발행부와 저장 콜백 연결. 이 브랜치는 `persistResult`와 `storedResults`를 제공하며, 실제 분석 엔진은 원 세션에서 통합한다.
- 다른 기기에서 기존 관리자 기록에 접근할 수 있는 계정 로그인 방식.
- 영상 파일 형식 제한. 현재 저장소는 파일 형식을 제한하지 않는다.

## 영상·평가 입력 연결 (10/9, `feat/supabase-video-persistence`)

이 브랜치는 기존 표와 RLS를 그대로 사용한다. SQL을 다시 실행하거나 공개 버킷으로 바꾸지 않는다. 실제 업로드·다운로드·새로고침 복원·다른 관리자 접근 차단을 확인했다. 브랜치 병합·배포 전에는 기존 웹 서비스에 적용되지 않는다. 상세 결과와 재현 방법은 [연결 확인 기록](STORAGE_VERIFICATION.md)에 있다.

- 화면의 대상자 ID(`Evaluation.id`)는 `people.id`다. 별도의 `assessmentId`를 발급해 `assessments.id`와 연결한다. 대상자를 다시 열 때는 가장 최근 평가를 불러온다. 평가 이력 선택 화면은 추가하지 않았다.
- 영상 저장에 동의한 다음 파일을 선택한다. 비공개 경로는 `{manager_id}/{assessment_id}/{무작위 파일명}`이며, 0바이트 파일과 50 MiB 초과 파일은 업로드 전에 거부한다.
- 새 파일 업로드와 영상 기록 저장에 성공한 뒤 화면의 영상을 교체한다. 실패하면 이전 파일을 유지한다. 교체 성공 후 이전 파일을 정리하며, 정리 실패 시 미참조 비공개 파일이 남을 수 있다.
- 선택 장면과 질문 답변, 건너뛰기 상태를 350 ms 지연 후 순서대로 저장한다. 실패한 입력은 같은 관리자 브라우저에 남기고 다시 저장할 수 있다. 저장 전 창을 닫으면 경고한다. 로그아웃 전에도 남은 입력을 저장한다.
- 자세별 `answers.__storage_path`는 답변이 어느 영상에 속하는지 구별하는 내부 필드다. 파일 교체와 답변 저장이 중간에 끊기면 복원 시 불일치한 장면·답변을 적용하지 않는다. 화면 질문에는 노출하지 않는다.
- `assessments.answers.__navigation.lastPath`는 이어서 입력할 화면 경로다. 기존 분석 결과·점수 필드는 덮어쓰지 않는다.
- 새로고침 시 같은 Auth 사용자 소유의 평가 입력을 복원하고, 현재 대상자의 비공개 영상을 인증된 `download`로 가져와 기존 `File` 기반 화면에 연결한다. 공개 URL이나 장기 서명 URL을 저장하지 않는다.
- 장면 확인 상태는 새로고침 후 다시 미확인으로 시작한다. 영상 교체 시 해당 영상의 장면·답변·확인 상태를 초기화한다. 건너뛴 영상은 다시 불러오지 않는다. 건너뛰기는 영상 삭제 기능이 아니며 기존 비공개 파일은 남는다.
- 예시 둘러보기는 DB에 평가·영상 데이터를 저장하지 않는다. 다른 기기에서 같은 익명 관리자 기록을 되찾는 기능과 자동 보관 기간 정책은 이번 변경에 포함하지 않았다.

원 세션 통합 대상: `frontend/src/lib/assessmentStorage.ts`, `evaluationStore.ts`, `VideoFilesProvider.tsx`, 영상 업로드·교체 화면, 저장 상태 표시. 엔진은 영상 `File`, 대상자 `id`, 별도 `assessmentId`, 영상 번호를 유지해야 한다. 이 브랜치의 `setFile`은 업로드 완료를 기다리는 `Promise<void>`다.

### 분석 결과 연결 계약

- VLM 확인·REBA 계산 뒤 `await persistResult(videoNumber, rebaResult)`를 호출한다. 기존 동기 `publishResult`는 화면 갱신용으로 유지하고, 사용자 확정 시 저장 콜백을 연결한다. 매 프레임·매 렌더마다 저장하지 않는다.
- `result.scene.timeSec`는 현재 영상의 `selectedTimes[videoNumber]`와 일치해야 한다. 입력 저장도 같은 순서 큐에서 선행한다.
- 미확정·측정 불가 결과는 최종 점수가 null이어야 한다. VLM 출처의 결과는 같은 장면에 대한 `confirmedBy: human` 근거가 필요하다. 동의 전 API 응답을 확인된 결과로 저장하지 않는다.
- `assessments.result`에는 `{schemaVersion: 1, videos: {영상번호: {storagePath, result}}}`를 저장한다. 모델·프롬프트·좌표·사람 수정 근거는 엔진 결과 안의 `evidence`를 보존한다. `measurements.videos`는 부위별 측정·채점 근거를 보관한다.
- 평가 전체의 `reba_score`는 건너뛰지 않은 영상이 모두 완료됐을 때 그 중 최고 점수다. 하나라도 미확정이면 null과 `needs_review`다. 입력·파일 변경 시 이전 점수와 결과를 무효화한다.
- `storedResults`는 현재 파일·선택 시각에 맞는 저장 결과다. 타입은 아직 `unknown`이며 원 세션의 `RebaResult` 계약으로 검증한 뒤 평가서에 표시한다. 입력이 미저장 중이면 예전 결과를 불러오지 않는다.

개발용 SQL: [DB 생성 파일](../supabase/migrations/20261009044810_safeangle_core.sql), [v6 평가 입력 추가 파일](../supabase/migrations/20261009051522_assessment_inputs_before_analysis.sql), [회사·작업 입력 삭제 파일](../supabase/migrations/20261009052807_remove_company_work_step.sql). 세 파일의 SQL은 Supabase 화면에서 실행했지만 원격 마이그레이션 이력에는 등록되지 않았다. 다시 실행하기 전에 이력을 맞춰야 한다.
